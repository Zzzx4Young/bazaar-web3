## 双数据库入口与可写就绪检查（2026-10-08）

API `/health/ready` 读取真实 PostgreSQL 的恢复状态与当前事务只读设置，
只读连接返回 503；`/health/live` 不依赖数据库。就绪检查不证明物理 fencing 或同步提交完成。

```bash

```

## 运行自动切换验收

首次在仓库根目录构建专用验证镜像，再执行后端验收：

```bash
sudo docker build --network=host -t bazaar-ha-patroni:4.1.5-pg17.11 infra/ha
cd backend
npm run test:postgres-ha:auto
```

需要 Node.js 22.12 以上、已安装后端锁定依赖及可执行 `sudo -n docker compose` 的权限。
双网络拓扑使用 Compose `gw_priority`，需要 Compose 2.33.1 以上；本机实际版本为 5.5.1。
构建的网络选项仅用于容器构建，不修改宿主机代理。镜像采用固定摘要的 PostgreSQL
17.11 与锁定 Python 依赖的 Patroni 4.1.5；Compose 中 etcd 3.7.2 和 HAProxy 3.2
也固定镜像摘要。初次运行需要拉取这些镜像。

脚本使用 `compose.ha-auto.yaml`，自动生成私有凭据、随机项目名、回环端口，
为两个写入代理分配各自固定的端口，容器重启后保持不变，其他节点使用动态端口，
以及三个 PostgreSQL 和三个 etcd 的独立持久卷。两个真实 API 使用受限数据库角色；
开发库不参与。结束后清理本轮项目、卷和临时凭据。报告位于已忽略的
`backend/.tmp/postgres-ha-auto-report.json`；失败时额外保留脱敏诊断日志。

2026-10-06 首次成功复测：50 笔通过两个 API 返回成功的订单及关联快照、配送、
预留、库存、事件、幂等记录在切换后逐条一致。强制停止主库后，原 API、数据库地址
和会话保持不变，29.386 秒后完成取消写入；新建订单也成功。旧主库重启后作为备库接入。
全部备库停止后的请求在 6 秒观察窗口内未成功，恢复一个备库后原幂等键重试成功。
随后强化复测也通过：29.414 秒恢复写入；确认没有复制连接后，新增写入在 15 秒
观察窗口内未返回成功。一个备库恢复到同步状态后，原幂等键写入及另一个 API 的
同键重放返回同一订单；数据库只有一笔订单、一条幂等记录，快照、配送、库存、
预留和事件完整，此前 50 笔订单仍与切换后基准一致。该轮报告记录了此强化复测。
这里证明该故障场景没有成功确认写入，不表示超时事务必定没有在主库本地提交。

随后同一完整脚本增加仲裁失去多数场景，2026-10-06 实测通过：

- 主库停止后的业务写入恢复时间为 29.342 秒，旧主库重新加入及无备库保护仍通过。
- 恢复全部数据节点并保存 52 笔已确认订单的全部关联记录后，强制停止两个 etcd。
  从停止仲裁节点到确认三个 Patroni 节点的 `/primary` 均返回 503、角色均不是
  primary，观测时间为 49.627 秒。此时间包含轮询和所有节点状态检查。
- 随后 15 秒内，两台原 API 交替执行 57 次同键新增订单请求，全部返回 500，
  没有成功确认。该轮应用仍返回内部错误，服务不可用语义当时尚未完善。
- 从恢复两个 etcd 到原 API 返回新增订单成功为 2.252 秒；故障前 52 笔订单及
  关联数据逐条一致，原会话有效。同键跨 API 重放返回同一订单，数据库只有一笔
  新订单和一条幂等记录。该轮脚本退出码为 0。

仲裁故障测试只检查确认降级之后的写入阻断；没有在降级前持续尝试业务写入，
也没有测量实际数据库降级时刻相对租约到期的关系。49.627 秒的状态观测不能证明
旧主库在租约到期前已完成隔离，仍需网络分区与更直接的数据库状态证据。
Patroni 默认依靠 DCS 租约更新维持主库资格；启用 failsafe 会改变 DCS 故障下的行为，
本轮没有启用该模式。依据 [DCS 故障处理说明](https://patroni.readthedocs.io/en/latest/dcs_failsafe_mode.html)。

### 仲裁端点与错误语义修复后的复测

扩展复测曾在 DCS 故障阶段失败，诊断显示已停止容器的 hostname 解析反复耗时数秒。
当时只记录了失败阶段，无法准确区分失败断言；现在失败日志额外记录脱敏异常原因。
本机固定三成员拓扑改为在 Patroni 启动时解析实际 IPv4 地址，并启用 `use_proxies`
关闭端点自动发现，避免重新导入成员广播的 hostname。仍连接三个独立 etcd，
没有增加仲裁代理，没有改宿主机代理或放宽 60 秒门槛。
参数行为依据 [Patroni 端点配置](https://patroni.readthedocs.io/en/latest/yaml_configuration.html#etcd)。
此方式仅用于成员不被替换的独立验证项目，不能直接套用到动态更换地址的生产集群。

随后故障链又捕获旧主库降为备库时的只读 SQL 错误。应用现集中识别数据库不可达、
连接关闭、池不可用及只读拒绝，返回 `503 / DATABASE_UNAVAILABLE / retryable=true`；
未知 SQL 缺陷仍是 500，业务冲突仍是 409。断线时服务端不自动重放事务，
客户端恢复必须保留原幂等键与请求。结构化错误优先；没有错误码的 pg 连接错误
只匹配已核对的完整固定消息，不按包含某个词的任意文本判断。

2026-10-06 最终完整故障链实测通过：主库停止后 29.431 秒恢复业务写入，
旧主库重新加入为备库；全部备库停止后的 15 秒内未返回成功，恢复后同键写入无重复。
停止两个 etcd 后 6.840 秒确认全部节点失去写入资格，随后 15 秒内两台原 API
的 57 次新增订单请求均为脱敏、可重试的 503。恢复多数仲裁后 2.471 秒恢复写入；
52 笔此前已确认订单及关联记录逐条一致，原 API、地址与会话保持有效，同键重放无重复。
该轮故障链尚未加入网络隔离；其状态观测不能替代实际数据库降级与租约到期时刻的核对。

### 主库与仲裁网络隔离

Compose 将 etcd 放在独立 `dcs` 网络，PostgreSQL 同时连接数据库与仲裁网络，
HAProxy 只连接数据库网络。数据库网络保持默认网关，宿主回环端口保持可访问。
脚本核对容器的准确项目标签后，仅断开当前主库的 `dcs` 网络，保留其数据库网络；
复原时使用检查得到的原地址，不改宿主机网络或代理。命令语义见
[Docker 网络断开](https://docs.docker.com/reference/cli/docker/network/disconnect/)与
[重新连接](https://docs.docker.com/reference/cli/docker/network/connect/)。

故障注入前同时核对两种真实来源：DCS `/sync` 中已发布的主库及同步候选，
以及 `pg_stat_replication` 中实际 streaming、sync 的备库。只有它们一致才开始
独立故障场景，不能将“两条复制连接存在”当作选主候选已就绪。
首次尝试没有这一前置核对：旧主库 13.373 秒确认只读、随后租约仍剩 6 秒，
但 60 秒内没有接管，验收失败。后来加入候选就绪检查后复测通过；没有保存首次
故障前的 `/sync`，因此不能断言那次失败全部由就绪窗口引起，也未证明恢复期间
连续叠加故障的可用性。

另一轮启动失败显示 Patroni 选择了已移除的 `/v3alpha`，随后收到非预期响应。
从固定版本源码推断，这是新 etcd 集群的初始版本报告与 Patroni 协议选择之间的
竞态；启动程序现等待三个真实端点都报告支持稳定 v3 的集群版本，再启动 Patroni。
依据 [Patroni 4.1.5 协议选择](https://github.com/patroni/patroni/blob/v4.1.5/patroni/dcs/etcd3.py)。
这是额外的协议就绪门槛，不将进程健康等同于协议就绪，不修改同步复制或 RTO 目标。

2026-10-06 最终完整故障链退出码为 0。隔离主库 `pg1` 后，直接 SQL 在 6.339 秒
确认 `pg_is_in_recovery()=true` 且 `transaction_read_only=on`；随后线性化读取的
leader key 仍属于 `pg1`，其原租约实际剩余 10 秒。租约 ID 按原十进制文本转 BigInt，
没有使用会损失 64 位精度的 Number。之后 `pg3` 自动接管，原 API 在隔离开始后
18.689 秒完成写入，原连接地址与会话不变，53 笔故障前已确认订单及关联数据一致。
同键跨 API 重放无重复订单、预留或事件；网络复原后旧主库回到备库并恢复两条复制连接。

报告的 `networkPartition.samples` 保存 71 次数据库状态及租约采样，
未观察到同时存在两个可写 PostgreSQL 节点。该证据针对本机这一隔离方式，
不证明采样间隙、任意网络分区、主机冻结或生产 watchdog/fencing 的安全性。

重新加入的首次尝试暴露启动配置写入问题：容器重启时不能覆盖 sticky `/tmp`
中由 postgres 拥有的配置文件。运行配置已移到独立权限 0700 的目录，配置文件为 0600；
修复后完成上述重新加入验收。此前失败不能计作通过。

## 拓扑与配置约束

- 三个 PostgreSQL 数据节点，一主两备；单主库故障后保留一主一备，继续同步提交。
- Patroni 管理角色、同步节点和旧主库重新加入；三成员 etcd 提供选主仲裁。
- 开启 `synchronous_mode`、`synchronous_mode_strict`，同步备库数量为 1，
  `synchronous_commit=remote_apply`。没有合格备库时禁止降为单节点或异步提交。
- 候选者必须遵守同步节点和时间线资格，不用管理员强制提升绕过数据保留约束。
- 本机候选配置为 `ttl=20`、`loop_wait=5`、`retry_timeout=3`、
  `primary_start_timeout=0`；满足 `loop_wait + 2 * retry_timeout <= ttl`。
  配置时间预算不证明 60 秒目标，必须测量实际业务写入恢复时间。
- 数据卷启用 checksums 或 `wal_log_hints`，允许 `pg_rewind` 将旧主库重新加入为备库。
- 稳定 TCP 写入入口通过 Patroni `/primary` 检查主库及选主锁，旧节点失去资格时关闭
  其现有数据库连接；两个 API 的连接 URL 和进程在主库切换时保持不变。
  该检查本身不证明有同步备库，失去全部备库的写入阻断必须另外验证。

以上依据 [Patroni 复制模式](https://patroni.readthedocs.io/en/latest/replication_modes.html)、
[动态配置](https://patroni.readthedocs.io/en/latest/dynamic_configuration.html)及
[REST 健康检查](https://patroni.readthedocs.io/en/latest/rest_api.html)。

## 本机实施顺序

1. 独立随机 Compose 项目、私有凭据、回环动态端口、三个独立持久卷；
   PostgreSQL、Patroni、etcd 及 TCP 入口使用明确版本，开发库不参与。
2. 初始化迁移和受限运行角色，等待三节点复制就绪并核对有效同步设置。
3. 两个真实 API 使用同一稳定写入入口；通过登录与订单接口准备业务数据，
   保存全部成功返回的订单 ID、快照、事件、预留和会话作为核对基准。
4. 强制停止当前主库容器，等待自动提升并通过原 API、原 URL 完成新的业务写入。
   从停止主库到该写入返回成功须不超过 60 秒；逐条核对所有已确认记录。
5. 重新启动旧主库，确认其只作为备库接入，追平新主库，且全程只有一个合格写入节点。
6. 停止全部备库，验证应用没有返回成功的新增写入；恢复一个备库后核对同步状态及写入恢复。
7. 仲裁失去多数及主库到仲裁网络断开已通过；继续测试入口连接切断、更多网络分区
   和进程冻结，检查隔离、选主资格和会话恢复。
8. 500 请求/秒、1000 用户混合负载已通过同步主备五分钟集中写入与 API 故障复测，
   通过配置为每 API 10 条连接，默认 5 条连接在该矩阵未通过；
   入口为 `npm run test:capacity:ha`，结果见[容量验收](../backend/CAPACITY.md)。
   当前实现两分钟持续负载的主库 SIGKILL 和全部备库失联均已通过：分别 29.287 秒和
   23.611 秒恢复原 API 写入，各核对 6000 笔故障模型订单；实际退出码和清理回执已保存。
   继续验证进程冻结及更广数据库故障矩阵；
   数据库切换期间的不可用请求、客户端恢复、已确认写入保留及 RTO 分别报告。

全部报告禁止包含凭据或私有连接字符串。脚本结束后仅清理本轮项目、卷和临时凭据；

## 生产边界

### Watchdog 默认必需与设备缺失验收

`infra/ha/watchdog_policy.py` 在任何启动网络请求、凭据读取或数据目录初始化之前应用策略：
默认 `mode=required`、`device=/dev/watchdog`、`safety_margin=-1`。
当前租约 20 秒，因此 watchdog 目标超时为 10 秒；启动校验要求该预算覆盖 HA 循环和
仲裁重试。不接受可选保护模式，设备路径只接受 Linux watchdog 路径。
启动器拒绝 `PATRONI_*` 原生环境覆盖，防止校验后改变集群身份或生效配置；支持的
覆盖项为 `HA_WATCHDOG_DEVICE` 和受限制的 `HA_WATCHDOG_MODE`。

仅 `HA_LOCAL_VALIDATION=1`、固定诊断 scope/namespace 且明确 `HA_WATCHDOG_MODE=off`
时允许关闭保护；`compose.ha-auto.yaml` 三个节点已显式声明此豁免。
所以本机正常故障回归仍属于无 watchdog 的诊断，不证明进程冻结时的物理隔离。
未挂载设备的默认启动不应通过降低保护级别来获得可用性。

从 `backend/` 运行 `npm run test:watchdog:required`，在无网络、只读、移除 capabilities、
非 root 且无宿主设备挂载的容器中调用已安装的 Patroni 4.1.5。
2026-10-08T12:08:15.948Z 实测：设备缺失时 `activate=false`、`running=false`、目标超时
10 秒；原生配置覆盖在启动初始化前被拒绝，两个容器均已清理。
报告 `backend/.tmp/watchdog-required-report.json` 记录不可变镜像 ID 和验证边界。
该结果证明缺失设备的拒绝激活及启动策略，不证明真实设备能在租约过期前复位旧节点。

本轮本机豁免下的正常故障链也通过，报告 `2026-10-08T12:08:33.593Z`，退出码 0：
主库 29.331 秒恢复写入，50 笔确认订单无丢失；全部备库停止时新建及回放均未成功确认。
仲裁多数丢失后 55 次探测均为 503；网络隔离时旧主库 6.337 秒只读，旧租约仍剩
10 秒，17.714 秒恢复新写入，53 笔确认订单及关联数据保留。

### 管理进程冻结：已复现的隔离缺口

从 `backend/` 运行 `npm run test:postgres-ha:freeze`。脚本只针对本轮随机项目，
核对容器归属后冻结实际 Patroni HA 子进程；PID 1 监督进程和 PostgreSQL 保持运行。
不能只向容器 PID 1 发送 STOP：当前 Patroni 会派生 HA 子进程，停住监督进程仍会续租。
首次这种无效注入已单独保留为 `invalid-supervisor-only-process-freeze-*`，不计产品验收。

实际子进程冻结结果（`2026-10-07T14:04:07.642Z`）：

| 观测 | 结果 |
|---|---|
| 原租约确认过期后旧 PostgreSQL 仍是主库且非只读 | 17.524 秒首次观测 |
| 同一轮直接 SQL 检查观察到新旧两个主库角色 | 19.961 秒 |

运行时 `watchdog` 为 `off`；“选主锁过期前旧主库已隔离”门禁失败。
这些 SQL 角色观测没有证明旧节点实际提交成功或已确认订单丢失，但足以否定隔离已验收。
当前失败报告及清理回执为 `backend/.tmp/postgres-ha-auto-process-freeze-report.json` 和
`backend/.tmp/postgres-ha-auto-process-freeze-run.json`；另有
`unprotected-manager-process-freeze-*` 备份，报告 SHA-256 已与回执一致性核对。
下一步须根据正式部署环境实施并复验 watchdog 或外部 fencing；本轮未改宿主机配置。

本机同宿主机容器不证明跨宿主机故障、持久盘损坏或机房失效下的可用性。
生产应把数据与仲裁节点分布到独立故障域，提供 TLS、受限管理网络、备份与恢复演练、
入口自身冗余及监控告警；同宿主机双 TCP 代理仍无法承受宿主机故障，HTTP 入口冗余未验收。

进程挂起或系统冻结时，仅靠 Patroni 主动降级不够：生产需要经过验证的 watchdog 或
外部 fencing，确保旧主库在选主锁过期前无法继续写入。
本机验证不操作宿主机 watchdog，也不能把强制停止容器的结果当作这项保护已验收。
依据 [Patroni watchdog](https://patroni.readthedocs.io/en/latest/watchdog.html)。

同步提交等待期间被取消的事务可能已在旧主库本地可见，但尚未向客户端返回成功。
因此 RPO 核对集合是成功响应确认的业务写入；失败或超时的写入保持原幂等键，
恢复后核对与重试，不能把未知提交结果当成确定未落库。
