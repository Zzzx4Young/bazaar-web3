# 后端架构与模块设计

更新：2026-09-09。状态：架构方向与技术主路线已确认；以下模块接口、实体归属、事务和运行方式为待评审设计，未实现。

决策依据：[ADR-0003](adr/0003-backend-architecture.md)。业务行为以 [Alpha 业务规格](server-alpha-spec.md) 为准，本文件不重写订单规则或扩展产品范围。

## 1. 系统边界

采用独立模块化单体：一个后端应用内部组织业务模块，不为每个模块单独部署服务。前端不直连数据库；后端模块不相互绕过业务方法写表。

建议请求路径：前端 → API 控制器（参数与身份）→ 应用用例（协调事务）→ 业务模块（规则与归属）→ PostgreSQL。统一入口按路径分流前端/API 是部署候选，域名和基础设施未定。

建议 API 采用 REST＋OpenAPI；这是接口设计建议，不是已批准的具体契约。业务数据模型、公开 DTO 和前端展示类型分离，不能将数据库实体原样返回。

## 2. 模块职责与数据归属

下列实体为概念模型，尚非数据库表或 ORM schema。

| 模块 | 职责与概念数据 | 不负责的内容 |
|---|---|---|
| 账户与权限 | Account、Session；预置账户、密码登录/退出、提供可信用户身份 | 不以统一登录检查代替各模块资源归属检查；无注册或管理账户 UI |
| 商品 | Listing；商品资料、发布状态、编辑、上下架 | 不修改订单或释放其库存 |
| 订单与库存 | Order、OrderSnapshot、InventoryReservation；订单转换、单件占用和释放 | 不直接签名链上交易；订单状态不等于资金状态 |
| 交付与异常 | DeliveryRecord、IssueRecord；物流单号、私有链接、补交、问题与退款请求记录 | 不单独认定资金已退回或商品已恢复可售 |
| 结算 | SettlementRecord；模拟付款/退款结果及幂等记录 | 不自行改变商品归属或交付事实；不接真实支付 |
| 媒体 | MediaAsset 候选；文件元数据、上传授权和读取权限边界 | 图片上传尚待确认；不自动托管数字商品交付文件 |
| 审计 | OrderEvent / AuditEvent；关键操作主体、对象、时间、结果 | 不保存密码、Cookie、提取码或完整敏感请求 |

订单业务事件与安全审计应按用途区分，避免无意义地重复存储所有字段。数据保留与清理周期在部署和数据设计阶段明确。

## 3. 依赖与事务协调

建议由应用用例层调用各模块公开方法，传递同一个事务上下文；ORM 已选 Prisma，具体事务 Client 传递与封装在技术契约中落地。禁止通过互相导入控制器或循环依赖协调业务。

| 用例 | 协作模块 | 一致性要求 |
|---|---|---|
| 创建实物订单 | 商品、订单库存、审计 | 校验可售、占用单件、创建订单与快照、记录事件在同一事务提交 |
| 取消未付款订单 | 订单库存、审计 | 校验主体与状态，只释放该订单占用；重复取消不重复释放 |
| 模拟付款 | 订单库存、结算、审计 | 结算结果与订单推进原子提交，失败不能只更新其中一方 |
| 提交交付或补交 | 订单库存、交付异常、审计 | 校验卖家和订单状态，追加交付记录并合法推进或保持异常 |
| 同意模拟退款 | 订单库存、交付异常、结算、审计 | 校验双方操作及退回结果，退款与订单状态一致；实物保持不可售 |
| 退款后恢复可售 | 商品、订单库存、审计 | 校验卖家确认、原退款与当前占用，单独恢复，不改原订单历史 |

并发控制建议采用事务内条件更新或行锁，辅以数据库约束；具体 SQL 与约束由数据设计确定。锁定顺序固定，事务尽量短，设置有限重试；不得在持锁事务中等待 RPC、上传或其他网络服务。

幂等记录需绑定用户、操作、请求标识及请求内容，防止重放或复用同一键提交不同业务内容。幂等不等于所有重复请求都返回成功，接口须明确冲突与合法重试。

## 4. 数据与基础设施

| 组件 | 设计角色 | 当前状态 |
|---|---|---|
| PostgreSQL | 核心业务事实、会话、库存、结算记录和操作历史 | 技术方向已确认，版本与 schema 未定 |
| Prisma | 数据访问、事务与迁移 | 用户已选，版本及关键事务与迁移验证待完成 |
| 对象存储（OSS/S3 等） | 如批准真实图片上传，存图片本体；数据库只存元数据 | 供应商、区域、上传范围未定 |
| Redis | 可选热点缓存、跨实例限流或队列依赖 | 不作为首期必需，不保存唯一库存事实 |
| 队列与 Worker | 可选图片处理、通知；未来链同步与对账 | 当前只设计运行边界，不自动批准功能 |

数据库连接池上限需考虑实例数、后台任务和管理连接，不允许 API 扩容无限增加数据库连接。列表限制分页大小、根据实际查询建索引；订单快照和金额精度遵循业务规格。初期不采用分库分表或独立搜索集群。

如实施上传：建议后端鉴权签发短期凭证、浏览器直传、服务端校验后标记可用；需设计配额、类型/内容检查、孤立文件清理及公开/私有访问分离。对象写入与数据库不是一个事务，必须允许失败重试与补偿。此段不是接入文件托管的授权。

## 5. 身份、安全与运行

建议密码安全哈希、成熟认证组件、数据库会话和 HttpOnly Cookie；认证库、会话期限、撤销和 CSRF 方案尚待技术评审。内测不取消鉴权、输入校验与防滥用保护。预置数据使用显式 seed，凭据不写入前端或版本库，不在应用启动时清库。

资源权限由对应业务模块验证：不信任前端传入的 buyerId、sellerId 或订单状态。私有交付、收件信息与公开商品 DTO 分离；公共缓存不得携带订单或会话数据。

建议 API 尽量无状态，后续可多实例运行。Worker 与 API 可以同仓库、复用模块但独立进程；这不等于拆微服务。当前无自动订单超时任务，不因为设计 Worker 而增加自动取消或退款。

生产化候选措施包括健康检查、优雅退出、结构化日志、请求 ID、延迟/错误率/锁等待/连接数监控、应用回滚与兼容迁移。备份需实际恢复演练；备份周期、恢复点目标、恢复时间目标与高可用等级尚待预算及部署范围确认。当前不承诺容量、SLA 或云费用。

## 6. Web3 扩展边界（不实施）

- 用户 ID 与钱包地址分离；未来 WalletBinding 属于身份扩展，但多钱包、钱包登录与恢复政策仍待产品确认。
- 订单状态与结算状态分离。当前只有模拟结算，未来链上实现允许异步确认、失败与撤销，不伪造 txHash 或复用模拟成功当链上成功。
- 链交易提交不代表结算完成。未来须校验链、合约、订单关联与事件内容；保存扫描进度、去重键、区块信息，定义确认与重组处理及对账。
- 模拟结算可同数据库事务提交；链交易与数据库不能这样处理。未来需独立的一致性与补偿设计，不能只替换一个结算函数。
- 链同步进程只通过受控业务入口推进状态，不绕过订单和结算校验。需要可靠消息时再评估事务 Outbox、重试和幂等消费者。
- 用户钱包、平台后台管理员、合约管理员和后台交易签名权限分离；不接收用户助记词或私钥，不在当前 API 中引入资金签名密钥。
- 公链、代币、Gas 代付、合约升级/暂停/裁决权限、异常退出及资金安全需测试网阶段另立规格。当前不自动超时、无完成后售后的内测规则不能直接作为真实资金合约规则。
